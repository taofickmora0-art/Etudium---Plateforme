# Bilan de la tâche 1.1 : structure des contenus (12 octobre 2026)

## En bref

- **Les contenus ont leur place dans la base** (migration `0004_contenus.sql`) :
  - parcours, formateurs, formations ;
  - une formation peut être dans plusieurs parcours ;
  - modules, leçons, contenus des leçons (vidéo, texte) et ressources ;
  - un espace de fichiers privé `ressources`.
- **La règle « qui voit quoi » est écrite une seule fois, dans la base** (spec §3) :
  - un visiteur voit le catalogue publié et regarde les leçons d'aperçu sans compte ;
  - une formation gratuite s'ouvre avec un compte ;
  - une formation payante reste verrouillée jusqu'au lot 2 ;
  - brouillons et formations archivées sont fermés ;
  - l'équipe (admin, modérateur, super-admin) voit et saisit tout. Le rôle formateur seul ne donne encore aucun droit (lot 4).
- **Garde-fous** :
  - l'adresse d'une formation publiée ne change plus ;
  - une formation publiée ne s'efface pas, elle s'archive ;
  - une adresse n'a ni point ni majuscule ;
  - un lien vidéo correspond à son fournisseur (YouTube ou Vimeo) ;
  - une ressource en consultation seule est un PDF ou une image.
- **Données d'exemple** (`web/supabase/exemples/lot-1.sql`, seulement pour la base de test) :
  - les 3 parcours et les 10 formations du design ;
  - la fiche complète d'Excel et sa formatrice ;
  - son programme : 4 modules, 12 leçons, dont 2 en aperçu.
- **Nouveau banc d'essai** : un vrai Postgres tourne dans les tests et exécute les migrations telles que tu les colleras dans Supabase. Il a rattrapé une erreur, une vidéo sans fournisseur qui passait. Les migrations du lot 0 y passent aussi, même rejouées.
- **Vérifications** : 326 tests automatiques, vérification des types et du code.

## Relecture finale

Aucun problème critique ni important. Le relecteur a lui-même vérifié, sur le banc, chaque point de vigilance du plan :
- brouillon invisible par la bande ;
- vidéo et fichiers verrouillés ;
- formateur sans droit de saisie ;
- fichiers qui se rejouent ;
- formation publiée protégée.

Rien ne devrait se comporter autrement dans le vrai Supabase.

## Points mineurs mis de côté

- La date de publication peut être saisie sur un brouillon : elle figerait alors son adresse et empêcherait de l'effacer. Seule l'équipe le peut, et le back-office ne l'enverra pas.
- La commande TRUNCATE (vider une table) n'est pas retirée aux rôles de l'API. Elle est inutilisable par l'API, mais contourne en principe « archiver au lieu d'effacer ».
- Quelques trous de tests :
  - fichiers d'une formation archivée ;
  - liens et ressources d'un brouillon ;
  - écriture du formateur ailleurs que dans les parcours ;
  - erreurs attendues sans motif précis.
- **Supabase affichera des avertissements dans son conseiller de performances :**
  - plusieurs règles de lecture sur chaque table ;
  - deux liens entre tables sans index.

  Sans gravité à cette taille.
- L'identifiant de compte des formateurs sera lisible par tous quand il sera rempli (lot 4) : à masquer à ce moment-là.
- Une vidéo Vimeo « non répertoriée » demande aussi son code secret dans l'identifiant : à prévoir avant les formations payantes (lot 2).
- Petites précisions de documentation : en-tête du fichier d'exemples, introduction du guide.

**À savoir pour plus tard** : recoller un ancien fichier SQL après un plus récent peut défaire ce que le plus récent a changé. Il faut toujours appliquer le plus récent, ou tous les fichiers dans l'ordre.
